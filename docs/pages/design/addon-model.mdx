# Addon model

roxy knows HTTP, not any particular application or API. Logic that needs to
understand the traffic goes in an addon: a layer downstream of the rules
that owns both lanes of every exchange it runs on. An addon is either:

- **a WASM layer** (`kind: wasm`): a WebAssembly component run in-process by
  `roxy-wasm`, written against the `roxy:addon` WIT package
  ([`wit/addon.wit`](https://github.com/roxy-proxy/roxy-proxy/blob/main/wit/addon.wit)),
  which hands each head over as one record and each body as a stream; or
- **a service layer** (`kind: service`): an external service in the network
  path, which each exchange streams through over a WebSocket
  ([service layer protocol](/reference/service-layers)).

## Two lanes

An exchange is two lanes. The request lane flows upstream, from the
client through the layers to the rules and the connector; the response
lane flows downstream, from wherever it starts through the same layers to
the client. Each lane is a head, bytes and an end, and the lanes carry no
HTTP rules of their own: what a head or a chunk means is for the two ends
of the proxy, the downstream socket and the upstream connector, to say.

A layer sits on both lanes of every exchange it runs on. On either lane it
may pass what it was given, hold it, rewrite it, or originate its own,
chunk by chunk, at any time. roxy infers nothing across the lanes: a
layer's answer on the response lane says nothing about the request lane,
which runs on upstream as the layer drives it. A layer that answers and
wants nothing forwarded forwards nothing; one that answers and forwards
has a forward that runs on for as long as it waits for the response to it.
Each layer must keep its output coherent for the next consumer. The
stack ensures that one valid request reaches the upstream socket and one
valid response reaches the client socket.

```
                 request ↓                                   ↑ response
 fixed   ┌─ CONNECT gate (SNI must match) ───────────────────────────────┐
 config  ├─ addon: first listed                                          │
 config  ├─ addon: second listed                                         │
 fixed   ├─ rules                  (admission ↓ / in flight ↑)           │
 fixed   ├─ address floor + deny lists (on the IP actually dialled)      │
 fixed   └─ connector ──▶ origin ────────────────────────────────────────┘
```

Addons always sit downstream of the rules, in the order listed under
`addons:`. A layer with a `when` runs only on the exchanges it matches
([choosing exchanges](/reference/addon-configuration#choosing-exchanges)).
Nothing configurable runs between the rules and the network, so what the
rules judged is what leaves.

The stack is a pipeline: every layer runs at once, as its own task, each
seeing what the downstream layer passed on. On a long stream each works
on a different chunk at the same time. Observe layers get copies and run beside
the stream rather than in it.

## Lanes, and the rules that move them

**Upstream** means toward the origin; **downstream** means toward the client.
The **client edge** connects the HTTP transport handler to the first pair
of lanes. The **core stage** is the upstream end of the chain: it validates
the final forwarded request, evaluates admission and in-flight rules,
applies destination restrictions through the connector, and owns upstream
processing through completion, including any WebSocket relay. Addon layers
run between these two stages.

Between two neighbouring stages (the client edge, each layer, the core
stage) run two lanes: a request lane, produced by the downstream stage and
consumed by the upstream one, and a response lane the other way. Each lane
is shaped like an HTTP/2 stream. Its producer may put on it at most one
head, then bytes, then trailers once, then either an end (complete) or a
cut (incomplete, with a reason); its consumer may stop it (read no more).
A lane that is ended or cut before any head carries nothing: a headless
request lane is no forward, a headless response lane from a layer is no
answer. A lane that has ended, been cut or been stopped is terminal and
never moves again; what a producer puts on a terminal lane is discarded.

The lifecycle rules are:

- **A stage is done** when its driver and body workers have finished.
  Ending an output lane does not by itself finish the stage: it may still
  consume its inputs or run host-service calls. Letting go of an unfinished
  input stops that lane.
- **A stop on a request lane** tells its producer and nothing else: the
  upstream stopped reading the forward, and the layer keeps its other
  lanes.
- **A stop on an unfinished response lane tears its producer down**: that
  stage and every stage upstream of it are cancelled. Unfinished outputs
  are cut and held inputs are released. Cancellation reaches stages even
  when an intermediate response has already ended. Releasing a completed
  response alone does not cancel a still-useful forward.
- **Client cancellation tears down the whole exchange**, independently of
  which response lanes have ended. HTTP/2 continues watching for stream
  resets while waiting for the exchange after an early answer.
- **A layer that lets go of its response lane without a head** has not
  answered: that is its `no_response` fault.
- **A layer that faults** (a trap, a budget, a missed deadline, a lane out
  of grammar, a reset, an invalid head attributed to it, or no answer) has its fault recorded before it is cancelled. If its response
  lane has no head, roxy puts the corresponding HTTP error response there
  for the downstream layers to handle like any other response.
- **A layer answered** if the response lane it consumes had no head when
  it put its own head on the lane it produces, decided then and never
  re-derived. The first fault recorded stands, and a layer's is logged
  once.
- **A layer cutting a lane it produces is an abort, not a fault**: the
  record says `forward_aborted` or `answer_aborted`, and the consumer sees
  an incomplete body. A headless response cut from an enforcing layer is
  still its `no_response` fault and generates a refusal.
- **A producer's end does not acknowledge delivery.** Its queued frames
  still belong to the consumer until read or discarded. Trailers are held
  until the clean end and length checks succeed, because HTTP trailers
  complete the message on the wire. Declared length is a validation
  property: an unfinished lane uses unknown-length HTTP/1.1 framing so
  even a cut after the declared bytes cannot look complete. HEAD and
  bodiless statuses commit at the head; their internal body still runs
  under the response idle deadline.
- **The exchange is over** when every lane is terminal, its consumers have
  finished or abandoned their bodies, and all drivers and enforcing
  host-service workers have returned. Upstream upload accounting is final
  before its owner returns. Guest drivers and their spawned `next`, endpoint
  and body-finish workers, service pumps and upload monitors belong to this
  barrier even when their parent is cancelled. Cancellation includes their
  actual destruction, not just an abort request.
  Both HTTP transports observe client loss through reclamation. The flow
  record is written after this barrier.
  WebSockets use the same rule: the core owns the relay and its accounting
  until it ends, then cancels any remaining layers.

Wire completion, exchange completion and connection lifetime are separate.
An HTTP/1.1 answer can finish while its upload or addon work continues;
reclamation keeps driving the request and any suppressed response body
concurrently. Only after reclamation can that connection serve a pipelined
request, and a late closing refusal still prevents reuse. A full pipeline
buffer has a [bounded reclamation deadline](/reference/limits#buffer-budget).

Observers are not stages: an observe layer gets copies of both lanes of a
hop, nothing it produces moves a lane, and the exchange does not wait for
it. A head-only layer puts its head on a lane and the body of the lane it
consumes in the same direction goes on with it (for a response, only when
the status is the same; otherwise the answer is the layer's own, whole).

## Request and response production are independent

A layer may answer before forwarding, while forwarding, or without ever
forwarding. A response head does not imply that the request lane has ended.
Responses can originate at any stage: the origin's response through the
connector, a refusal from the rules or address checks, a layer's own
answer, or a `503` generated for a failed layer. Each enters the response
lane at that stage and flows downstream through the layers before it
like any other response: a layer sees the rules' `403` from `next` as it
would see a `403` from the origin, and may pass it on or replace it with a successful response. Addons are trusted
configuration, so that is theirs to decide; the request did not leave, and
the flow log records the rules' verdict whatever the client was given
([in the proxy](/reference/addon-configuration#in-the-proxy)).

A layer answering without forwarding and the rules refusing are the same
event at different stages: the request lane ends there, that stage
produces the response, and nothing further upstream ever sees the request.

A body that stops short upstream of a layer (an in-flight deny cut it, the
origin's body failed) ends that lane with the failure, not the exchange:
the layer sees the lane end short of complete and finishes its own lanes
as it sees fit. Only the client's own request failing ends the exchange
outright, since nothing can answer a client whose request broke.

## The two ends of the proxy enforce validity

The lanes are opaque. What reaches a socket is not: the request the last
layer passes upstream is re-validated as strictly as a client's and judged
by the rules, and the response the first layer passes downstream is
re-framed as strictly as an origin's. A head that cannot go out where it
arrives (a second final response head, a `101` that relays no upgrade, a
`1xx` other than a relayed `101`) is the fault of the last layer that
touched it, and becomes a response on the lane downstream of it like any
other failure; a body that does not match the length its head declared is
cut, since its head is already out. Between the two ends a layer may do as
it likes with what it holds, so long as what leaves it is something the
next layer can carry.

## Ordering across layers

Two things come out of a layer, and roxy orders only one of them.

The exchange's bytes form a pipeline. A head or a chunk reaches layer B
only after layer A has sent it on, and A may hold, rewrite or drop it on
the way: what B reads is what A passed, in the order A passed it, and the
rules admit the request the last layer forwarded. The response is the same
pipeline in the downstream direction: the rules see the upstream's bytes
first, then B, and A gets a chunk only after B has passed it. This holds
for enforce layers of either kind. An observer is in neither order: it reads a copy
beside the pipeline, holds nothing up, and can neither tag nor write
state, so the rest of this section is about enforce layers.

Host-service effects are not in that pipeline. `add_tag`, `state_put`,
`record` and `quarantine` run independently of the request and response
lanes. Each layer has a worker that runs its calls in order. There is no
implicit ordering between one layer's call and another layer's read:
A's `state_put` and B's `state_get` are concurrent unless A awaits its `result` before sending the bytes B will read. B cannot read on
a chunk it has not received, so the await puts A's write ahead of B's
read. A WASM layer's call is a synchronous function that returns before
the layer continues, so it has that order by construction; a service layer
sends the call as a message and awaits the `result` itself
([host services on a stream](/reference/service-layers#host-services)).

So, to make an effect visible:

- **to the layers upstream**: await the `result` before sending the head or
  chunk whose handling should see it (a WASM layer's call has returned by
  the time it sends anything);
- **to this exchange's admission rules**: land it before the request is
  forwarded, so before the layer calls `next` or the service sends its
  forwarded `request` head;
- **otherwise**, the write is seen by the next rule that reads it. A tag
  lives on this exchange, so that is an in-flight re-check of it; state
  persists, so it is that or a later exchange's admission. The write does
  not itself trigger a re-check: a rule runs when a value it watches
  changes, and reads the tag or key then. A write never reopens a decision
  already made ([policy evaluation](/design/policy-evaluation#evaluation)).

## Invariants

1. **The rules evaluate every request that leaves.** An addon can reshape
   traffic freely; its output is re-validated by the canonical model and
   then judged by the rules exactly as if the client had sent it. On the
   way back, the in-flight rules see the upstream's response before any
   addon does.
2. **Every layer is held to the workload's limits.** Whatever a layer passes
   on is treated as if a client sent it: header limits, body caps, idle
   timeouts. A layer cannot pass on `CONNECT`: a tunnel is something the
   client opens at the proxy port, never a request to forward.
3. **Failure is closed.** A layer that traps, exceeds a budget or passes on
   an invalid head produces a `503` on the lane downstream of it, which the
   layers there may reshape but the client gets if none does; after the
   response head is out, the body is cut. There is no "on error, pass";
   observe mode is the one safe way to run a layer whose failures must not
   matter.
4. **One forward and one answer per layer.** A layer sends the request lane
   upstream at most once and the response lane downstream exactly once. In
   which order, and how far apart, is its own affair.

## Who is blamed

When an exchange fails, one party is blamed, and the first fault recorded
stands. Every party records its own fault before anything downstream of it
can fail on it: a layer as it fails, before its bodies end; a body where it
enters the stack, before a layer reads it; the transport handler when it
cancels the exchange. So what a layer makes of a body or a `next` that ended on
someone else's failure is a consequence, never a second fault.

- A layer's own failure (a trap, an exceeded budget, an invalid head, a
  service that broke its stream) is the layer's: `503` with
  `terminal_rule: layer:<name>` before the response head, a cut body after
  it, and one `layer_error` event either way. The `503` travels downstream
  on the response lane, so a layer there may reshape what the client gets;
  the record is the refusal's either way. A failure found upstream of the
  layer that caused it (a passed-on request that does not validate, say) is
  put down to the nearest enforcing layer downstream of it.
- A client upload that breaks is the client's, as without a stack: the
  connection closes on the parse error before the head, the body is cut
  after it, and no `layer_error` is logged however many layers fail on the
  cut body.
- An upstream response body that fails before any layer has answered with
  a head of its own is the upstream's: `502`, `reason: upstream_body_failed`.
  One that fails after that ends the response lane upstream of the layer
  with the failure; what the client's response makes of it is the layer's.
- A body the [buffer budget](/reference/limits#limits) cannot cover on its
  way to a layer (a decoder's window) fails closed as the budget's:
  `reason: buffer_budget_exhausted`.
- An observer is never blamed, and a client that gives up is nobody's
  failure: nothing is logged.

## One exchange, one `next`

A layer calls `next` at most once per exchange; a second call traps. The
stack carries the client's traffic and nothing else: a layer never
originates requests through the layers upstream of it, so retrying, regenerating
or replaying is the client's job, and a layer that rejects something
answers with a response the client can act on. Anything else a layer needs
to reach is a [named endpoint](/reference/host-services#endpoints-endpoints),
which goes straight to the connector, never through other layers or the
rules.

`next` and the layer's answer are the two lanes, and neither waits on the
other. A layer may answer first and forward after, forward and answer
before the response from upstream arrives, or answer and never forward.
Its answer reaches the client as soon as it is made. A forward is carried
upstream only while something downstream waits for its response: a layer
that wants its forward delivered reads at least the response head. A layer
that stops reading the response (drops the pending response, or returns
without reading it) has the upstream request cancelled; the forward's body
is still the layer's to finish or cut. A layer that cuts a lane of its own
(drops a body unfinished) has aborted it: nothing comes back for a cut
forward, and the record says `forward_aborted` or `answer_aborted`; that
is not a failure. A layer that fails is torn down, and everything upstream
of it with it. Once a layer is done with the client's upload, the rest of
it is dropped rather than held for a reader that will never come.

## A layer takes what it subscribes to

A layer subscribes to each direction in config: the head and the body
(`full`, the default) or the head only. Of a direction it has in full, a
layer may read, rewrite, split, delay, inject into or replace the stream,
chunk by chunk. roxy buffers nothing on a layer's behalf; a layer that
wants a whole body reads it, within its `max_memory`. The patterns:
observe (`next(req)`, return its response unchanged), rewrite in flight
(wrap a body stream in a transform), withhold until cleared (forward a
streamed response as it arrives but hold back parts, say tool calls, until
judged), and deny or answer (return a response without calling `next`).

A body a layer is not subscribed to bypasses it, as if the layer had
passed it on untouched: the layer sees the head with an empty body and
decides at admission, and roxy splices the body onto what it passes on. An
enforce layer still denies or rewrites at admission; an observer that wants
heads only costs no body copies
([what a layer sees](/reference/addon-configuration#what-a-layer-sees)).

A WebSocket is an exchange like any other, only long-lived: after the
`101`, the request body carries the client's bytes and the response body
the upstream's ([WebSockets through addons](/reference/addon-configuration#websockets)).
Layers see bodies decoded, so none needs its own decompressors
([content codings](/reference/addon-configuration#content-codings)).

## Modes

- `mode: enforce` (default): the layer is in the path and its decisions
  take effect.
- `mode: observe`: roxy tees both lanes to the layer and ignores
  anything it returns except host-service calls such as `record`. The
  layer cannot change or delay traffic, so its failures cannot weaken
  containment: a trap or missed deadline is logged, not fatal, which makes
  it the way to deploy an uncalibrated monitor. `sample` gives it a share
  of the matching exchanges, and an observer may `record` but cannot tag
  the flow ([capabilities](/reference/addon-configuration#capabilities)).

  Each copy of a body the layer is subscribed to is buffered for it, so
  one that keeps up sees every body in full, however large. A copy is cut, and the flow goes on, when
  the layer falls `limits.max_observer_lag_bytes` behind, the
  [buffer budget](/reference/limits#limits) cannot cover its next frame,
  or no instance of the layer comes free within its `first_byte_timeout`
  (`observer_lagged`, with the `reason`). A request refused or answered
  upstream of the observer without its body being read ends the copy
  where reading stopped, without an error, and the observer sees the refusal
  from `next`; a copy that fails (the client went away mid-upload) ends
  with that failure, so the layer can tell the two apart.
