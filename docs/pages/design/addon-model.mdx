# Addon model

roxy knows HTTP, not any particular application or API. Logic that needs to
understand the traffic goes in an addon: a layer downstream of the rules
that owns both lanes of every exchange it runs on. An addon is either:

- **a WASM layer** (`kind: wasm`): a WebAssembly component run in-process,
  written against the `roxy:addon` WIT package
  ([writing addons](/guides/writing-addons)); or
- **a service layer** (`kind: service`): an external service that each
  exchange streams through over a WebSocket
  ([service layer protocol](/reference/service-layers)).

How to configure one, and exactly what it sees and how it fails, is in
[addon configuration](/reference/addon-configuration).

## The stack

```
                 request ↓                                   ↑ response
 fixed   ┌─ CONNECT gate (SNI must match) ───────────────────────────────┐
 config  ├─ addon: first listed                                          │
 config  ├─ addon: second listed                                         │
 fixed   ├─ rules                  (admission ↓ / in flight ↑)           │
 fixed   ├─ address floor + deny lists (on the IP actually dialled)      │
 fixed   └─ connector ──▶ origin ────────────────────────────────────────┘
```

Addons sit downstream of the rules, in the order listed under `addons:`.
Nothing configurable runs between the rules and the network, so what the
rules judged is what leaves. The stack is a pipeline: every layer runs at
once, as its own task, each working on what the layer downstream of it
passed on. On a long stream each works on a different chunk at the same
time.

## Lanes

Between two neighbouring stages (the client edge, each layer, the core)
run two lanes: a request lane going upstream and a response lane coming
back. A lane is shaped like an HTTP/2 stream: at most one head, then bytes,
then optional trailers, then an end (complete) or a cut (incomplete). Its
reader may stop it. The lanes carry no HTTP rules of their own; what a
head or a chunk means is for the two ends of the proxy to say.

A layer may pass on what it was given, hold it, rewrite it, or make its
own, chunk by chunk, on either lane. The two lanes are independent: a
layer may answer before forwarding, while forwarding, or without ever
forwarding, and roxy infers nothing about one lane from the other.
Answering without forwarding and the rules refusing are the same event at
different stages: that stage produces the response, and nothing upstream
of it sees the request.

A few rules follow from the shape:

- **No head, no message.** A request lane ended without a head is no
  forward. A response lane a layer lets go of without a head is no answer,
  and that is a fault.
- **A layer cutting its own lane is an abort, not a fault.** The next
  stage sees the body incomplete. A cut that follows a fault or the
  client's loss is not an abort: it is how that failure reaches the next
  stage.
- **Stopping the response gives up the forward.** A layer that stops
  reading the response to its forward has the forward, and every stage
  upstream of it, cancelled. Stopping the request lane only tells its
  producer.
- **A response is a response wherever it starts.** The origin's, a
  refusal from the rules, a layer's own answer, or the `503` roxy puts on
  a failed layer's lane all travel downstream through the layers the same
  way. A layer may pass on or replace the rules' refusal: addons are
  trusted configuration, the request did not leave, and the flow log keeps
  the rules' verdict.
- **One forward and one answer per layer.** A layer calls `next` at most
  once and answers exactly once. It never sends requests of its own
  through the layers upstream of it: anything else it needs to reach is a
  [named endpoint](/reference/host-services#endpoints-endpoints), which
  goes straight to the connector.

A layer subscribes to the head only, or the head and the body, of each
direction. A body it is not subscribed to bypasses it, as if it had passed
the body on untouched, and costs no copies
([what a layer sees](/reference/addon-configuration#what-a-layer-sees)).

## The two ends enforce validity

What happens on the lanes between layers is the layers' business. What
reaches a socket is not: the request the last layer passes upstream is
re-validated as strictly as a client's and judged by the rules, and the
response the first layer passes downstream is re-framed as strictly as an
origin's. A head that cannot go out is the fault of the last layer that
touched it.

## Ordering across layers

Two things come out of a layer, and roxy orders only one of them.

The exchange's bytes form a pipeline. A head or a chunk reaches layer B
only after layer A has sent it on, so what B reads is what A passed, in
the order A passed it. The response runs the same way downstream: the
in-flight rules see the upstream's bytes first, then B, then A.

Host-service effects (`add_tag`, `state_put`, `record`, `quarantine`) are
not in that pipeline. Each layer's calls run in order on its own worker,
beside the lanes. A's `state_put` lands before B's `state_get` only if A
awaits its result before sending the bytes B will read. A WASM layer's
call returns before the layer goes on, so it has that order by
construction; a service layer awaits the `result` itself
([host services on a stream](/reference/service-layers#host-services)).

So, to make an effect visible:

- **to the layers upstream**: await the result before sending what they
  should see it with;
- **to this exchange's admission rules**: land it before the request is
  forwarded;
- **otherwise**, it is seen by the next rule that reads it, in flight on
  this exchange or at a later one's admission. A write never reopens a
  decision already made
  ([policy evaluation](/design/policy-evaluation#evaluation)).

## Invariants

1. **The rules judge every request that leaves.** A layer's output is
   re-validated and judged exactly as if the client had sent it. On the way
   back, the in-flight rules see the upstream's response before any layer
   does.
2. **Every layer is held to the workload's limits.** Whatever a layer
   passes on is treated as a client's: header limits, body caps, idle
   timeouts. A layer cannot pass on `CONNECT`.
3. **Failure is closed.** An enforcing layer that fails puts a `503` on
   the lane downstream of it before the response head, and cuts the body
   after it. There is no "on error, pass". One party is blamed for a
   failed exchange: the first to fail
   ([failure](/reference/addon-configuration#failure)).

## Modes

- `mode: enforce` (the default): the layer is in the path and its
  decisions take effect.
- `mode: observe`: roxy copies both lanes to the layer and ignores
  anything it produces except host-service calls such as `record`. It
  cannot change or delay traffic, so its failures are logged, never fatal.
  That makes it the way to run an uncalibrated monitor. An observer that
  falls behind loses its copy; the exchange goes on
  ([observers](/reference/addon-configuration#observers)).
