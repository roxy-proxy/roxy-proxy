# Overview

roxy is a programmable, TLS-intercepting HTTP firewall built for streaming. Each exchange flows through the addons that match it, which can rewrite, answer or block it mid-stream, and a strict policy layer underneath decides what actually leaves. It is meant for workloads you don't fully trust: AI agents, CI jobs, sandboxes and third-party code.

Clients use it as an explicit `HTTP_PROXY`, or reach it through its own DNS if they ignore proxy settings ([DNS steering](/deploy/dns-steering)). roxy decides what each request may reach, holds the credentials the workload needs so the workload never sees them, and logs every decision as a line of JSON.

roxy terminates TLS with certificates from its own CA, so addons and rules see the decrypted traffic. It parses each request into one canonical form and sends that form upstream. Ambiguous input is rejected, not guessed at. Request smuggling and header injection don't reach the upstream, and what the rules matched is exactly what is forwarded.

Bodies stream. Requests and responses flow through addons and rules chunk by chunk, in both directions, and nothing is buffered unless a layer or a rule asks to read a whole body or message. A long upload, a server-sent event stream or a WebSocket is one long exchange: it passes through as it arrives, for as long as it lasts. A slow addon slows it down rather than cutting it off.

The policy is one YAML file. Rules are a list of allows plus the denies that restrict them. A matching deny always wins, and anything no rule allows is denied. Rules can read the request head, and they can keep watching the bodies and the response as they stream. Metrics give you rate limits and byte budgets.

Logic that needs to understand the traffic goes in an addon: a WASM component that runs in process, or an external service that the traffic streams through. Addons can rewrite, withhold, answer or block, mid-stream if they need to. Each addon runs only on the requests its `when:` condition matches, and an observing addon can sample a share of them. A flow no addon runs on reaches the rules as the client sent it. Addons always sit above the rules, so whatever an addon passes on is judged by the rules again, and no addon can get round them.

It fails closed. If roxy can't parse, verify or classify something, it denies it. A broken config is not loaded, a failing addon denies the flow, and a missing metric or secret denies rather than allows.

## Use cases

- [AI agents](/use-cases/ai-agents): allow the model APIs and source hosts an agent needs, inject provider keys at the boundary, cap uploads and rate-limit writes.
- [CI jobs](/use-cases/ci): read-only access to the registries a build needs, no route anywhere else, a log of every fetch.

## A policy

```yaml
default: deny

secrets:
  openai: { env: OPENAI_API_KEY }

rules:
  - id: github-reads
    when: host under "github.com" and method in [GET, HEAD]
    then: allow

  - id: openai
    when: host == "api.openai.com" and path starts_with "/v1/" and method == POST
    then:
      - set_header: { authorization: "Bearer ${secret:openai}" }   # the client never sees the key
      - allow

  - id: upload-cap                         # watches the body as it streams
    when: host == "api.openai.com" and body.bytes > 10mb
    then: { deny: { status: 413 } }
```

You can try a policy without sending traffic:

```sh
roxy rule test --config roxy.yaml POST https://api.openai.com/v1/responses
```

The full language is in [rules](/reference/rule-language).

## What roxy is not

roxy is not a transparent gateway. It decides what passes through it, and it can't stop traffic that never reaches it. To contain a workload, the network has to give it no route out except through roxy. [Containing a workload](/deploy/overview) gives the recipe.

roxy speaks HTTP/1.1, HTTP/2 and WebSockets to clients. Raw TCP doesn't pass. The [principles](/principles) page sets out the threat model: what roxy prevents and what it doesn't try to prevent.
