# AI agents

An agent runs code you didn't write, on instructions it read from places you don't control. Put roxy in front of it. roxy allows the model APIs and source hosts the agent needs and holds the provider keys. It caps what the agent can send, and it logs every request, including the ones it refused.

## A starting policy

The agent can call Anthropic's API, read from GitHub and install packages. roxy holds the API key. Writes to GitHub are rate-limited, and uploads are capped.

```yaml
version: 1
default: deny

listeners:
  - name: proxy
    bind: 0.0.0.0:3128

tls:
  ca_dir: /var/lib/roxy/ca

secrets:
  anthropic: { env: ANTHROPIC_API_KEY }

metrics:
  - id: github_writes
    count: requests
    where: host under "api.github.com" and method in [POST, PUT, PATCH, DELETE]
    window: 1m

rules:
  - id: anthropic
    when: host == "api.anthropic.com" and path starts_with "/v1/"
    then:
      - set_header: { x-api-key: "${secret:anthropic}" }   # replaces whatever the agent sent
      - allow

  - id: github-reads
    when: host under "github.com" or host under "githubusercontent.com"
    then: allow

  - id: github-writes
    when: host == "api.github.com" and method in [POST, PATCH]
    then: allow

  - id: packages
    when: >-
      method in [GET, HEAD] and
      (host == "registry.npmjs.org" or host == "pypi.org" or host == "files.pythonhosted.org")
    then: allow

  # Denies restrict the allows above. Order does not matter.
  - id: no-write-burst
    when: metric.github_writes >= 30
    then: { deny: { status: 429 } }

  - id: upload-cap
    when: body.bytes > 10mb
    then: { deny: { status: 413 } }
```

What each part does:

- **`anthropic`** sets `x-api-key` from a secret. The agent can send any placeholder (its SDK may insist on one). roxy replaces it before forwarding, and the real key never enters the agent's environment. Injected values are redacted from the flow log.
- **`github-reads`** allows `github.com`, `api.github.com`, `codeload.github.com` and the `githubusercontent.com` hosts with any method. Narrow it if the agent should only read.
- **`no-write-burst`** denies the 31st write in any minute with a `429`. The metric counts denied requests too, so probing the limit isn't free.
- **`upload-cap`** reads `body.bytes`, so it watches each upload as it streams and stops it at the chunk that crosses 10 MiB. Nothing past that chunk is forwarded.

Everything else gets a `403` and a flow log line naming `_default`.

Check it before you deploy:

```sh
roxy check --config roxy.yaml
roxy rule test --config roxy.yaml POST https://api.anthropic.com/v1/messages
roxy rule test --config roxy.yaml --metric github_writes=30 POST https://api.github.com/repos/a/b/issues
```

## Containing the agent

roxy only decides what passes through it. The agent needs no route out except through roxy: no direct TCP, no UDP, no DNS. roxy resolves names itself, so the agent needs no resolver. The [quickstart](/quickstart) does this with an `internal: true` Docker network. [Deployment](/deploy/overview) has the recipe for other setups.

Point the agent at roxy and make it trust roxy's CA:

```sh
export HTTP_PROXY=http://roxy:3128 HTTPS_PROXY=http://roxy:3128
export http_proxy=$HTTP_PROXY https_proxy=$HTTPS_PROXY
export SSL_CERT_FILE=/path/roxy-ca.pem
export NODE_EXTRA_CA_CERTS=/path/roxy-ca.pem
export REQUESTS_CA_BUNDLE=/path/roxy-ca.pem
```

## What you get for free

- **No private networks.** roxy denies loopback, RFC 1918, link-local and other private ranges after it resolves each name, so the agent can't reach the cloud metadata endpoint or your internal services through an allowed name. DNS rebinding doesn't help. See [address floor](/policies/address-lists#address-floor).
- **No smuggling.** roxy re-serialises every request in one canonical form. A header the agent splits or folds is rejected, not passed on. See [HTTP](/reference/http).
- **An audit trail.** Every exchange is a JSON line with the rule that decided it. See [flow log](/operate/flow-log).

## Going further: judge the traffic

Rules know HTTP, not what the agent is trying to do. To judge the content of a request, such as a tool call, a prompt or an outgoing file, add an [addon](/addons/overview). An addon sits above the rules and owns both streams. It can call a model of its own through a named endpoint, with credentials roxy attaches, and it can deny, rewrite or answer.

```yaml
addons:
  - name: sentinel
    kind: service                      # an external service the traffic streams through
    endpoint: sidecar
    mode: observe                      # log what it would do; switch to enforce when ready
    endpoints:
      sidecar: { url: "http://127.0.0.1:9000/layer", private_ok: true }
```

[inspect_sentinel](https://github.com/meridianlabs-ai/inspect_sentinel) runs as a service layer like this to supervise an agent at the boundary. Whatever an addon passes on, the rules judge again, so an addon can't widen the policy.
