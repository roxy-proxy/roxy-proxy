roxy

Node protocol

The protocol between a roxy node (a roxy process in node mode) and its control plane (any server implementing these four operations). The contract is spec/node-protocol/v1/openapi.yaml: the example bodies here are checked against its schemas in CI and titled with the schema each satisfies.

A node enrols once with a bootstrap token and receives a node token, then authenticates with it to poll for its lease, ship its flow log and renew the token. The lease is the whole policy: a rendered roxy.yaml, the secret values it names, and how long it is good for. An expired lease denies everything. The control plane never pushes; the node polls.

Transport

  • HTTP/1.1 or HTTP/2 over TLS; all paths start with /roxy/v1/. Bodies are JSON, Content-Type: application/json; unknown fields are ignored by both sides. The node's User-Agent is roxy/<roxy_version>.
  • Every request carries Authorization: Bearer <token>: the enrolment token at enrolment, the node token everywhere else. The node presents no client certificate, so the control plane can sit behind any TLS terminator; a token only ever travels inside the server's TLS. A request other than enrolment whose token the server does not recognise is answered 401.
  • Bootstrap material, given out of band: the control plane URL, an enrolment token, and optionally a PEM bundle of CA certificates to verify the control plane with (otherwise the system roots).

Errors

Every non-2xx response carries an error body: error is a stable code, message is for humans, and a 426 adds missing (unsupported versions). A node acts on the status code, not the body.

Error
{"error": "invalid_token", "message": "enrolment token not recognised"}

Enrol

POST /roxy/v1/enrol with Authorization: Bearer <enrolment token>.

EnrolRequest

fieldmeaning
roxy_versionthe node's roxy release; a server may refuse one below its floor with 426
protocol_version1; a server that does not speak it answers 426 with missing: ["protocol_version:1"]
EnrolResponse
{
  "node_id": "node-7f3a9c",
  "token": "nt1-9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
  "not_after": "2026-11-05T10:12:00Z",
  "renew_after_seconds": 1296000
}
fieldmeaning
node_idchosen by the server: 1 to 128 characters from A-Z a-z 0-9 . _ -; stable for the life of the node
tokenthe node token: 1 to 512 bytes of RFC 6750 b64token text (A-Z a-z 0-9 - . _ ~ + /, then any number of =), opaque to the node, which stores it and presents it unchanged as Authorization: Bearer on every later request. Its lifetime and storage (hashed at rest is recommended) are the server's decisions
not_afterwhen the server stops accepting the token, RFC 3339 in UTC
renew_after_secondscounted from receipt; once passed, the node renews. Well inside the token lifetime, so a failed renewal can be retried. Whatever the value, the node renews no later than two thirds of the way to not_after and no sooner than one second after receipt; it does not check the schema's minimum, so 0 renews once a second

The enrolment token's lifetime and reuse (single-use, shared across a fleet) are the control plane's decisions; single-use with a short expiry is recommended. The node writes the node token, with its node_id and not_after, to its state directory (mode 0600): the only credential the protocol puts on disk, and a revocable per-node identity.

Renew

POST /roxy/v1/renew with the node token and the enrol body; the response has the enrolment response's shape, with node_id unchanged and a fresh token. The server keeps accepting the old token until its own not_after, so a renewal that has reached one replica but not another cannot lock the node out; the node switches to the new token on receipt and replaces the one in its state directory.

5xx, timeout, connection and TLS errors are retried with backoff, and so is a 401: the replica answering may not yet know the token the last renewal issued, so the node keeps trying under the token it has, logging once per run of them. 410 is terminal; a 426 or other 4xx is logged once and ends renewal, and the token serves until its not_after. Once it expires the node exits non-zero with an error naming the remedy (a new enrolment token and an empty state dir), as it does on a start whose stored token has already expired: no control plane recognises the token, so nothing short of re-enrolment recovers the node.

Lease

POST /roxy/v1/lease with the node token. The body is the node's state:

  "roxy_version": "0.1.0",
  "protocol_version": 1,
  "uptime_seconds": 86400,
  "policy_state": "loaded",
  "spooled_bytes": 0,
  "seq_unreserved": false,
  "quarantine": null
}
fieldmeaning
lease_idthe lease the node holds; null before the first. Lets the server notice a node that did not apply what it was sent
roxy_versionthe node's release; the server may refuse to serve it with 426
policy_statenone (no lease yet), loaded (a lease is in force) or expired (the lease ran down, or the node is revoked). A quarantine does not change it: the lease is still applied, and quarantine says the node refuses everything regardless
spooled_bytesflow-log data accepted but not yet acknowledged
seq_unreservedtrue while events are being tagged with seq values past the node's persisted reservation, because a flow.seq write is failing or has not caught up. A restart in that state may reuse those seq values, and the server would drop the reused events as duplicates; a node reporting true for long needs its state directory looked at. Absent from a node that predates the field
quarantinethe quarantine in force, or null. Absent from a node that predates the field
QuarantineReport
{
  "id": "q-01J9ZB7QX4R2M8K3N5P6T7V8W9",
  "since": "2026-10-13T09:14:02Z",
  "cause": {"kind": "rule", "rule": "exfil-guard", "flow": "01J9ZB7P"}
}
fieldmeaning
idminted by the node per incident; what a release names
sincewhen it tripped, on the node's clock
causewhat tripped it, as the node's quarantined flow event carries it: kind: rule with the rule id and the flow, kind: threshold with the listener, the counter (parse_errors), its count and window_seconds, or kind: layer with the layer name, the flow and, when a service layer tripped it, call, the service's id for the call (flow log)

The server answers 200 with the full lease on every poll (no conditional fetch), or 410, 401, 426, 5xx as in the errors table.

Lease body

Lease
{
  "lease_id": "lease-01J9Z8K3",
  "valid_for_seconds": 900,
  "refresh_after_seconds": 300,
  "config": "version: 1\nlisteners:\n  - name: proxy\n    bind: 0.0.0.0:8080\nsecrets:\n  github: { lease: true }\nrules:\n  - id: github\n    when: host == \"api.github.com\"\n    then: [allow]\n",
  "secrets": {
    "github": "ghp_example"
  },
  "state_epoch": "2026-10-06T09:00:00Z",
  "flow": {
    "ship": true,
    "batch_max_bytes": 1048576,
    "flush_interval_seconds": 5,
    "spool_high_water_bytes": 67108864,
    "on_high_water": "hold"
  },
  "quarantine": {
    "release": ["q-01J9ZB7QX4R2M8K3N5P6T7V8W9"]
  }
}
fieldmeaning
lease_idopaque; changes whenever any other field changes. The node reports it on every poll and quotes it in flow batches
valid_for_secondsa duration, not an instant: the node sets valid_until = sent_at + valid_for_seconds from its own clock, sent_at being just before it sent the request, so a slow answer shortens the lease and clock skew has no effect. The server's clock is never used
refresh_after_secondswhen to poll next, counted the same way; leave room for several retries before valid_for_seconds runs out (a third of it is reasonable). The node never polls later than halfway through the lease
configa complete roxy.yaml as a string, with no secret values: every secrets: entry the lease supplies is name: { lease: true }
secretseach secret name the config declares, to its value, a UTF-8 string. The node reads a missing map as empty, which refuses the lease if the config declares any lease: true secret
state_epochopaque. When it differs from the previous lease's, the node clears every rule set_state entry and every metric window before applying the lease (how a control plane lifts a lockout a rule imposed with set_state); unchanged, state survives a config change. The first lease sets it without clearing anything
flowflow upload settings. ship: false turns shipping off; the other fields are still required. on_high_water is hold (apply roxy's backpressure to traffic when the spool is full) or spool (drop the oldest spooled events, logging once)
quarantinereleases of the node's quarantine. release lists incident ids the control plane has released; the node lifts its quarantine when the quarantine.id it reports is among them, and ignores any other id, so a release decided before a later trip lifts nothing. Ids may stay listed indefinitely. Orthogonal to the policy: the rest of the lease is applied whether or not the node is quarantined, so the policy is current the moment the quarantine lifts. Optional; a server that has released nothing leaves it out
interception_careserved; a v1 server does not send it and a v1 node ignores it (the node accepts any value here, whatever the schema says)

The node applies only what differs from what it holds: a changed config rebuilds the policy (the atomic snapshot swap of a file reload); changed secrets alone swap the in-memory secret map and update the redactor, leaving rules, addons and upstream pools alone; neither changed only moves valid_until. A lease is applied in full or not at all: a config that roxy check would reject, or a secrets map missing a name the config declares, is logged and discarded, and the node keeps the lease it has. A node without a lease denies everything and reports not ready.

Unsupported versions

A node reports protocol_version and roxy_version at enrolment, renewal and every lease fetch. A server that does not speak the protocol version, or will not serve nodes below some roxy release, answers 426 naming what the node lacks:

Error
{"error": "unsupported", "message": "roxy 0.1.0 is below this server's floor of 0.2.0", "missing": ["roxy_version:0.2.0"]}

There is no other capability negotiation: the node parses config strictly, so a lease using something it does not understand fails to load, and the lease_id on its next poll shows the server it was not applied.

Flow upload

POST /roxy/v1/flows with the node token. The body may be gzip compressed, signalled with Content-Encoding: gzip.

FlowBatch
{
  "node_id": "node-7f3a9c",
  "lease_id": "lease-01J9Z8K3",
  "seq_first": 1042,
  "events": [
    {"seq": 1042, "ts": "2026-10-06T10:12:00.123Z", "event": "request", "flow": "01J9Z8", "decision": "deny", "terminal_rule": "_default"},
    {"seq": 1043, "ts": "2026-10-06T10:12:00.410Z", "event": "log", "flow": "01J9Z9", "rule": "audit"}
  ]
}
fieldmeaning
node_idmust match the node the token names, or the answer is 400 node_mismatch
lease_idthe lease in force when the batch was assembled; any lease id issued to the node is accepted
seq_firstthe seq of the first event; events are consecutive and in order from it, or the server answers 400
eventsflow log records with seq added: a per-node counter that increases by one per shipped event, persisted in the state directory in blocks so it keeps increasing across restarts (a restart skips to the end of the last reservation, at most two blocks of 1024)

A batch is at most the lease's batch_max_bytes (the JSON before compression); the node flushes when that is reached or flush_interval_seconds has passed since the first unsent event. A server that refuses a batch within the size it stated is treated as 5xx.

FlowAck
{"acked_through": 1043}

Delivery is at least once: the server stores the batch, deduplicating on (node_id, seq), and answers 200 with the highest seq it has stored for the node; the node drops spooled events at or below acked_through. A gap within one run means events were dropped (spool mode at the high water): a server-side alert, not a protocol error. Restarts and ship: false also leave gaps.

responsenode behaviour
400 (node_mismatch, a lease_id the server never issued, events not consecutive)logged apart from an outage; the batch is unshipped audit and stays spooled, so under hold traffic stalls until the control plane accepts it
507log once and apply on_high_water to what accumulates until a new lease arrives; the control plane is expected to revoke the node or issue it a new lease
410shipping stops, and so does the drain that follows a 410 on the lease: a control plane that wants a revoked node's last events keeps accepting its batches
401, 5xxas in the errors table
