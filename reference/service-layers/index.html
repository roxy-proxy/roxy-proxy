roxy

Service layer protocol

A kind: service layer is an external service at its position in the stack exactly as a WASM layer is (addon model). The exchange's two lanes stream through it: the request streams into it and it streams back the request to forward, if it forwards one; the response from upstream streams into it and it streams back the response the client gets. It may pass bytes through, rewrite or hold them, or originate its own, on either lane, at any time. Each lane each way is shaped like an HTTP/2 stream: a head, body bytes, trailers, and an end, or a cut; its reader may stop it.

addons:
  - name: sentinel
    kind: service
    endpoint: sidecar                   # one of this addon's endpoints
    mode: enforce                       # enforce | observe
    endpoints:
      sidecar: { url: "http://127.0.0.1:9000/layer", private_ok: true }
    limits:
      first_byte_timeout: 2s            # to get a stream, then to the service's answer, with no clock while its forward is upstream; an observer's end (default 30s)
      max_connections: 4                # per endpoint (default 4)
      max_streams: 100                  # exchanges at once per connection (default 100)

path and the WASM limits are refused on a service layer; max_connections and max_streams are refused on a WASM layer, and at zero. capabilities and config mean the same for both kinds (host services).

Transport

Long-lived WebSocket connections to each endpoint, each carrying many exchanges as streams.

  • Subprotocol roxy.layer.v6; a service that does not accept it fails the handshake.
  • The URL is the endpoint's (http → ws, https → wss, with the upstream's certificate verification), dialled through the connector (the address floor and deny lists apply), never through other layers or the rules. The handshake carries the endpoint's headers. Each connection is an endpoint_call event against the flow whose exchange opened it.
  • Pooling. A new exchange takes a stream on an idle connection if there is one; otherwise it opens a connection while the endpoint has fewer than max_connections; otherwise it takes the connection with the fewest streams, and once every connection has max_streams streams it waits for a free one within first_byte_timeout. Concurrent exchanges spread across connections because each connection is one reader and one writer on each side: a service that handles each connection on one task gets one core per connection. Idle connections stay open. A connection that closes or fails fails its in-flight exchanges closed; later exchanges go to another connection.
  • Reload. New exchanges get new connections, dialled under the new policy and secrets. Old connections take no new streams: an idle one closes at once, a busy one when its last exchange ends.

Frames

Text frames are JSON control messages, each with a stream field. Binary frames are body bytes: a 4-byte big-endian stream id, one direction byte (0 request body, 1 response body), then the bytes. roxy numbers the streams on a connection from 1 upward and never reuses a number.

A stream opens with an open message from roxy:

{"type":"open","stream":7,"flow":"01J…","conn":"01J…","layer":"sentinel",
 "mode":"enforce","subscribe":{"request":"full","response":"head"},
 "client_ip":"10.0.0.5","listener":"proxy",
 "sni":"api.example.com","tags":["a","b"],
 "capabilities":["state","record"],"config":{"reject_at":0.8}}

client_ip is client.ip as the rules see it (fields). sni is left out when there is none. capabilities are the layer's grants, and config its config: value, what a WASM layer reads through flow.config. subscribe is the layer's subscription: for a direction it names head, roxy sends the head and its end with no bytes between, and the service answers the same way; bytes the service sends for that body fail the exchange closed (unsubscribed:<direction>), and the body the service did not see goes on with the head it passed on. Declared lengths validate bodies; open lanes use unknown wire length so a later cut remains visible (what a layer sees). The pair (flow, layer) is unique and stable (two layers using the same endpoint in one flow get separate streams with different layers), so a service can key its state on it.

Every message carries stream; it is left out below.

Each direction of the stream is a lane each way. A lane's events, in order: at most one head, bytes, at most one trailers, then one end. An end may come before a head: the lane then carries nothing. A lane whose end carries "error" is cut: what came before it is not the whole. Trailers are delivered to the consumer only after a clean end and successful length validation, because sending HTTP trailers completes the message. Declared lengths validate bytes; an unfinished lane uses unknown-length framing on HTTP/1.1 even when the service supplied content-length. Its terminal chunk is withheld until the clean end. HEAD and bodiless statuses complete on the HTTP head itself; their internal response lanes are still consumed under response_body_idle_timeout, and a later failure cancels remaining work without changing the already-complete HTTP response.

ruledetail
headsurl is absolute; headers are end-to-end fields as a WASM layer sees them (no hop-by-hop or framing fields), at most limits.max_headers of them in a head or trailer section the service sends: more is a protocol violation. content-length is present when the length is known and not zero; one the service sends is enforced: more or fewer bytes than declared is a protocol violation
header valuesbyte strings: each byte is the code point of the same value (ISO-8859-1), so obs-text bytes (http.allow_obs_text) read as Latin-1 and go back as the same bytes. A code point above U+00FF is a protocol violation
trailersa request trailers the service sends is held to a client's rules (trailers): it needs http.allow_request_trailers, fits limits.max_header_bytes, and may not carry a framing, routing, authentication or content-* field. One that breaks them is the service's invalid_request: the forward never completes, and the exchange is refused 503, layer_error, or the error is logged if a response head is already out. A response trailers is held to an origin's rules as it is written to the client
orderon each lane, from each side: head, bytes, trailers, end. Bytes or trailers before their head or after their end, a second head, a second trailers, a second end: each is a protocol violation. The two lanes are independent, and so are the two sides: roxy sends its response head as soon as the layer upstream answers, even while the client's body is still arriving; the service sends its request at most once and its response exactly once, in either order, and may send either while the other lane is still streaming. A request_end with no request before it forwards nothing. Answering says nothing about forwarding, and a service that wants nothing forwarded forwards nothing
cutsan end that carries "error" cuts its lane: the bytes before it are not the whole. From roxy, the body stopped short on its way (an in-flight deny cut it, the upstream's body failed, the client gave up, the service's own forward was cut); the text is for diagnostics only, is not stable, and may be another layer's own. The stream, and the service's own lanes, go on. A response_end with "error" and no response before it says nothing came back for the forward: it was cut. From the service, a cut is its own doing and not a fault: the exchange's record says forward_aborted or answer_aborted, and what is downstream of the cut lane sees it cut. If the service cuts its response lane without ever providing a head, roxy also records no_response and generates a refusal. An error on the end of a head-only lane, which carries no body to cut, is a protocol violation
stopstop says its sender reads no more of that body: the receiver sends no more of it, need not end it, and credits nothing for it. roxy sends stop for the request lane when the upstream stops reading the forward. A service that stops the response lane gives the forward up: nothing upstream carries a response nobody waits for, so the upstream request is cancelled. A service that stops the request lane keeps everything else
enda stream ends when all four lanes are terminal (ended, cut or stopped), output body validation has finished, and every accepted host-service call has queued its result. Ending the service's two output lanes leaves the input lanes available: an early answer can finish before the upstream response arrives. A stopped forward upload does not stop that response. The service must read or stop each input; stop on the response input gives up the forward. A service that forwards and never answers is failed by its clock once the upstream outcome arrives. Either side may abandon a stream with reset; roxy sends no further lane data after a reset, and a service reset fails an enforce exchange closed. An opening abandoned before open went out sends no reset. Valid host calls crossing a retired stream's end receive a result error; other messages are ignored and body bytes are not credited
flow controlper stream and per body, each way. Each body of a stream starts with 256 KiB of credit each way; the receiver grants more with credit as it consumes, and the sender may have no more bytes of that body outstanding than granted. roxy grants in steps of 64 KiB as its feeder enqueues frames into the bounded lane channel. That channel holds two frames in addition to the credit window: 256 KiB frames can leave 768 KiB of unread payload per body before the final consumer reads. See buffer bounds. Sending past credit is a protocol violation. Control messages are not counted

A stalled physical WebSocket writer backpressures every stream on that connection. Directional credits allow independent progress while the socket is writable; the priority control queue can bypass queued data but cannot bypass bytes already waiting on the socket.

Host services

A service reaches the host services a WASM layer has by message, each behind the same capability granted in the layer's capabilities, and answered by the same host: a call means the same, is refused for the same reasons and fails the layer with the same layer_error.kind (and the exchange with it, in enforce mode), whichever kind of layer makes it. Every call carries an id of the service's choosing (an unsigned 64-bit integer) and is answered with a result carrying the same id: value is what the call returns (null for a call that returns nothing), error a refusal of what the service passed or a call arriving after stream retirement.

A call may be sent at any point while the stream is open, including part-way through a body. Calls run in order, one at a time per stream, beside the bodies: they neither wait for nor hold up the heads and bytes, and roxy promises no order between a call and the heads or bytes the service sends after it. The service orders it: it awaits the result before sending whatever the effect must precede, be that the request, the response or the rest of a body (ordering across layers). A call's tag or state write is seen by this exchange's admission rules only if it lands before the request is forwarded; otherwise by the next rule that reads it: for a tag, which lives on this exchange, an in-flight re-check of it; for state, which persists, that or a later exchange's admission. A write does not itself trigger a re-check (#509). At most 64 calls may be waiting, and more is a protocol violation. Accepted calls keep the stream open until their results have been queued, including when all four lanes have finished. To issue a new call, send it before the last lane becomes terminal. Calls queued before a reset still run, retain the stream's reservation while they run, and are logged if they fail; their results have nowhere to go. A valid call arriving after retirement receives a result error and has no effect. This covers a call crossing roxy's last input end on the wire. At most 64 such refusals may wait to be written on a connection; exceeding that limit closes the connection.

A call without its capability, a log message or a record kind and document together over 64 KiB, an add_tag, state_put or quarantine from an observer, or a full state store fails the layer (layer_error, kind capability:<name>, budget:message, budget:tags or host) and resets the stream: in enforce mode that fails the exchange, in observe mode the exchange goes on. The result error reports a refusal of what the service passed, or a call arriving after stream retirement. roxy's own record of a call names its id as call: on the layer_record a record writes, on the layer_error a failed call causes, on the operational log line a log writes, and on the cause of the quarantined event a quarantine trips. endpoints.call has no message: a service calls what it needs itself.

Migration from v5

roxy.layer.v6 is incompatible with roxy.layer.v5 and the experimental roxy.layer.v0. Update the WebSocket subprotocol on both peers together. Each side must handle stop, trailers, explicit ends in both directions, and headless completion. Keep receiving upstream input after both service outputs end, and explicitly stop inputs the handler will not consume. Outstanding host calls now receive results before normal stream retirement. The bundled Python helper implements this contract. Incompatible protocol changes use a new subprotocol name so older peers fail at negotiation.

WASM layers use roxy:addon@0.3.0; rebuild components with the matching SDK and WIT. Components using roxy:addon@0.2.1 or the experimental unversioned package must be rebuilt. Package versions remain part of the interface identity for future incompatible changes.

Semantics

  • The forwarded request gets the same checks as a WASM layer's next: re-validated as strictly as a client request, then judged by the rules. What comes back on the response lane is whatever the upstream stages produced: the upstream's response, the rules' refusal, or an HTTP error response for a failure upstream. The service may pass on or reshape any of these responses. The service's own response is handled as a WASM layer's.
  • Deadlines. first_byte_timeout bounds getting a stream, then the service's answer, as it does a WASM layer's: from roxy's request head until the service answers or forwards. The clock is suspended while its forward awaits an upstream outcome. A response head or a headless response_end restores the whole budget, unless the service has already answered; receiving a head does not wait for the response body to end. An expiry of the original request budget cannot consume or suspend this renewed answer budget. An observer gets that budget from roxy's last message to end its stream. A stream has no overall deadline. Head-only output lanes still require their explicit end: bypassed bytes can flow before it, but completion waits for both the end message and the bypassed body. This includes a HEAD or bodiless response already completed on the client connection. Body-idle and upstream timeouts still apply while the service's answer clock is suspended. The client edge applies response_body_idle_timeout even to a HEAD or bodiless response it must discard, and observes client loss through final reclamation.
  • An early response goes to the client at once, however far the forward upstream has got, and its body is the client's response from then on; the response from upstream still arrives on the service's lane for it to read. If the stack upstream fails after that, what arrives is the HTTP error response for that failure, or the lane ending with the error if its body had started; the service's answer stands either way. The forward runs on only while the service waits for its response (the end rule above).
  • Failure is closed in enforce mode: a failed connection or handshake, a protocol violation (bad JSON, a message out of order, bytes of a body that is not open, an invalid head, a broken length, bytes past the credit), a missed deadline, a reset from the service or a lost connection denies the exchange (503, layer:<name>) before the response head and cuts a streaming body after it. A cut body never reaches either peer as complete; HEAD and bodiless responses have already completed at the head. layer_error.kind is service:connect, service:protocol, service:timeout or service:closed; bytes of a head-only body are unsubscribed:<direction>. A response_end with no response before it is no answer: no_response.
  • A body that fails on its way to the service is not its failure: its lane ends with the error, no layer_error is logged, and the stream goes on (who is blamed).
  • One stream's failure is its own: a violation resets that stream only. Broken framing fails the whole connection: a text frame that is not a JSON object with a valid stream, a binary frame shorter than its 5-byte prefix or with an unknown direction byte, or a stream id roxy never opened. Every exchange on it fails closed (service:protocol) and roxy closes it.
  • Observe mode uses the same streams: the service gets copies of both directions; credit is honoured, reset ends the stream and is logged (layer_error, service:closed), host-service calls run as in enforce mode (less the ones an observer may not make), and the heads, bytes and ends the service sends go nowhere. The stream ends after all four lanes and accepted host calls finish, as in enforce mode. A stop from the service ends the corresponding copy. So a service can read the copies through and then record what it saw before ending the stream, as a WASM observer can. From roxy's last message the service has first_byte_timeout to end the stream, or roxy fails it (service:timeout); a cut copy (observer_lagged) is reset. Waiting for credit is falling behind, so grant extra credit as an observe stream opens (roxy_layer.py grants 16 MiB per body). Body bytes the service sends on an observe stream are discarded and credited back in steps of 64 KiB; past credit is still a violation.
  • WebSockets run through the stream (addon configuration). The 101 from upstream arrives as roxy's response head, and the service answers with a 101 of its own. At the client edge, only final statuses 200–599 or a 101 for a real upstream upgrade are accepted; intermediate lane heads may be rewritten by a downstream layer before reaching it. After the upgrade, the request body carries the client's bytes and the response body the upstream's, with no length cap on either, until each side closes; the stream holds its place on the connection for as long as the WebSocket is open. roxy sends no request_end before the 101, so a service that waits for the end of the request body never forwards an upgrade and fails on first_byte_timeout: forward as the request arrives. When the relay ends, roxy closes the client's connection and resets the stream if its bodies have not both ended.

The quickstart's sidecar, roxy_layer.py, is the service side of the protocol for asyncio: it handles streams, credit and resets and hands a handler one exchange at a time.

The helper rejects a host call with ProtocolError if the stream ends while the call waits to send. Such an unsent call does not keep the stream open. A call already sent keeps its result waiter; if it crosses retirement on the wire, roxy's refusal raises HostError.

The Python helper exposes received trailers through trailers and response_trailers. Its byte-iterator forwarding helpers do not send trailers; a service using those helpers must not assume trailer-preserving passthrough.

The Python helper's Exchange.forward raises ForwardEnded when the upstream response lane ends without a head. A handler may catch it and answer locally. If it propagates, the helper ends its response lane headless; it does not reset the stream. A handler that supplies no answer still gets no_response; the forward ending is not a service protocol fault.
