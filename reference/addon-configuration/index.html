roxy

Addon configuration

Addons are listed under addons:, in the order they wrap the exchange (addon model). Each entry is a WASM layer or a service layer; the two kinds share most keys.

addons:
  - name: sentinel
    kind: wasm
    path: /etc/roxy/addons/sentinel.wasm
    mode: enforce
    when: host == "api.anthropic.com" and path starts_with "/v1/messages"
    subscribe: { request: full, response: head }
    capabilities: [state, record, endpoints]
    endpoints:
      monitor-model:
        url: https://api.anthropic.com/v1/messages
        headers: { x-api-key: "${secret:monitor_key}" }
        timeout: 10s
      threat-intel:
        url: https://ti.internal:8443/score
        path: prefix
        private_ok: true
    limits: { max_memory: 128mb, first_byte_timeout: 30s }
    config: { reject_at: 0.8 }
 
  - name: monitor
    kind: service
    endpoint: sidecar
    mode: observe
    sample: 0.1
    subscribe: { request: head, response: head }
    endpoints:
      sidecar: { url: "http://127.0.0.1:9000/layer", private_ok: true }
    limits: { first_byte_timeout: 2s, max_connections: 4, max_streams: 100 }

limits

Limits catch a broken layer, not a slow one: a slow layer makes its exchanges slow, not denied, with one exception. Exchanges that keep every instance busy past first_byte_timeout cost the exchanges queued behind them, which are denied rather than wait (max_instances below). Each is optional.

keykinddefaultwhat it bounds
first_byte_timeoutboth30show long a layer may hold a head, request or response, before passing it on or answering: its own time only (starting an instance, its work, endpoint calls, reading the body it was given), never time next spends waiting for upstream. Overrun fails the layer closed (budget:first_byte_timeout for a WASM layer, service:timeout for a service layer), and the exchange with it in enforce mode. A service layer gets one budget to obtain a stream and a fresh one when the upstream outcome reaches it, including a headless end, until it has answered; an observing one gets a last from roxy's final message to its own end of the stream. It bounds the layer's own time, not the exchange's: body-idle and upstream timeouts still apply while the answer clock is suspended (service layers). It also bounds the wait for an instance when all max_instances are busy, on its own: an enforce exchange that gets none within it is denied (layer_error, no_instance); an observer loses its copy (observer_lagged, no_instance)
max_memorywasm64mblinear memory per instance, summed over the instance's memories; table growth and the host resource table (4096 live resources: body streams, pollables, pending responses) are capped too. What a layer holds of a body lives here. An interpreter in WASM (Python) needs 128–256 MiB
max_instanceswasm1024live instances, so concurrent exchanges and, with max_memory, the layer's memory. An exchange that finds none free waits first_byte_timeout for one, then fails closed (no_instance), so the clients holding every instance cannot queue the rest indefinitely. Instances start on demand
recycle_after_exchangeswasm10000an instance is replaced after this many exchanges; 0 replaces it after every exchange
recycle_above_memorywasmthree quarters of max_memoryan instance whose memory passed this is replaced after its exchange. At most max_memory
max_connectionsservice4WebSocket connections to the endpoint
max_streamsservice100exchanges at once on one connection; past max_connections × max_streams an exchange waits for a free stream within first_byte_timeout

The layer's head deadline stops once it answers. Bodies may stream for longer, subject to the client's and upstream's body idle timeouts. The client edge applies response_body_idle_timeout even when consuming an internal body that HEAD or a bodiless status prevents it from sending. WebSockets have the relay's idle timeout. There is no total CPU budget: a guest yields on an engine-wide 1 ms tick so other tasks can run and cancellation can stop it.

What roxy check refuses

A missing path or one that does not exist; endpoint not among the addon's endpoints; a key of the other kind (path and the WASM limits on a service layer; endpoint, max_connections and max_streams on a WASM layer); sample on an enforcing layer, or outside (0, 1]; a zero max_instances, max_memory, recycle_above_memory, first_byte_timeout, endpoint timeout, max_connections or max_streams; recycle_above_memory above max_memory; a when that reads body.*, response.* or ws.*, or an unknown metric or list; a subscribe value other than head or full.

Capabilities

A layer has no access outside its own streams. capabilities grants it named host services, which a WASM layer calls and a service layer sends as messages:

capabilitygrants
endpointsendpoints.call: outbound calls to the layer's named endpoints, with roxy attaching the headers
stateflow.state-get, flow.state-put: the state store the rules use
recordflow.record: structured events in the flow log
metricsflow.metric-get: read a metric for this flow's key
logflow.log: roxy's operational log
quarantineflow.quarantine: put the whole proxy into quarantine; enforce only

Every import is linked whatever is granted (one binary runs under any set); an ungranted call traps with CapabilityDenied and fails the layer (the exchange with it, in enforce mode). flow.current, flow.add-tag and flow.config need no capability; flow.add-tag from an observe layer is refused by the host (layer_error with kind: host: the observer fails, the exchange goes on), since a tag steers the when of the layers upstream. There is no secrets capability: credentials go on an endpoint's headers.

Behaviour

What a layer sees

subscribe names what the layer gets of each direction. With full (the default) the layer owns that direction: it reads the body, chunk by chunk, and what it passes on is the body that goes on. With head the layer gets the head with an empty body and no content-length, and the body bypasses it: whatever the layer passes on (the head it gives next, or the head it answers with) carries the body it did not see, spliced on by roxy.

  • An enforce layer can still deny, rewrite or answer at a head it is subscribed to; the bodies stream past it at no cost in copies or buffering.
  • A response head-only layer answers with the status it was given to pass the response on with its head edited; the body from upstream follows. Any other status is an answer of the layer's own: its body stands and the body from upstream is dropped, so a layer can refuse at the response head. A layer that answers without next resolving answers whole too, since there is no body from upstream.
  • A layer that passes on bytes of a body it is not subscribed to fails the exchange closed: a 503 before the response head, a cut body after it, layer_error with kind: unsubscribed:request or unsubscribed:response. An open lane has unknown length on the wire, including a bypassed body. HTTP/1.1 uses chunked framing so a later cut remains visible after the last declared byte; any declared length still validates the body.
  • A head-only observer gets copies of the heads and no copy of the body, so neither the lag budget nor the buffer budget is touched for it.
  • The rules are not affected: they judge the request that leaves the stack, head and body, whoever supplied each.
  • Bodies are decoded for the layers, and a WebSocket relayed without extensions, only when some layer that runs is subscribed to a body (content codings, WebSockets).

Streaming protocols

Lanes carry HTTP structure: one head, streaming body bytes, optional trailers, then an end or cut. They resemble an HTTP/2 stream's lifecycle; they are not HTTP/2 wire streams. Request and response lanes are independent, so a layer can answer while it holds a request, or keep answering while it holds an upstream response for approval.

protocol or featuresupport and limits
SSE, NDJSON, streaming JSON, multipart responses and HTTP-based MCPbodies stream as bytes. Chunk boundaries need not match application messages; a layer editing them must parse the application's framing
gRPCthe lanes support concurrent request and response bodies and trailers such as grpc-status. Service layers can receive and send trailers explicitly. The Python helper exposes received trailers but its forwarding methods do not send them. WASM host-side body.passthrough preserves trailers, but the WASI byte streams do not expose trailers for reading or rewriting; copying bytes into a new stream does not preserve them. For SSE approval, a full-body layer can publish a 200 text/event-stream head and send a start event or comment such as : approval pending\n\n. It can keep sending comments while it holds the request or buffers selected upstream events. Once approved, it forwards the request or writes the approved or edited events into its existing response body, then streams subsequent events. A refusal after that head is an application event in the same response, not a new HTTP status. A second response head fails the layer and cuts an answer already in progress.

Keepalive bytes must reach the client within its idle timeout and roxy's response_body_idle_timeout. They do not extend a client's absolute deadline, an endpoint-call timeout, or an upstream timeout. SSE comments are valid only for an SSE body; gRPC requires correctly framed gRPC messages, and its HTTP/2 PING is connection control rather than body data.

Choosing exchanges

when is a rule language condition over admission fields. A layer runs only on the exchanges it matches; the rest pass it at no cost (no instance, no body pumping, no service session).

  • when sees the request as it reaches the layer: what the downstream layer passed on, re-validated. A downstream layer can steer a request into or out of an upstream layer's when.
  • It may read admission fields, headers, the query, state[..], metric.<id> and address lists. body.*, response.* and ws.* are config errors.
  • tag["x"] sees tags set by enforce layers downstream, not the rules' tags (the rules run upstream of the layers).
  • An unavailable input (a metric, an address list, a missing value under an operator that cannot answer for null) fails the flow closed like a layer failure (503, layer_error with kind: when:<code>), never skips the layer. On an observe layer the failure is logged and the layer gets no copy.
  • A layer when skipped on a WebSocket's upgrade request is not in that WebSocket's byte path.

sample (observe only) is drawn from the flow id, so it is the same for a flow however often it is asked.

In the proxy

The stack is a chain of stages joined by lanes (addon model): the client edge adapts the HTTP/1.1 connection or HTTP/2 stream and puts the client's request on the first lane, each layer runs on its own task, and the core stage validates the forwarded request, evaluates admission and in-flight rules, applies destination restrictions, and owns the upstream connection and any WebSocket relay. A layer's answer goes to the client as soon as the layer gives it; a forwarded request continues upstream while the layer waits for its response. The flow is logged once every lane is terminal, its body has been read or discarded, and all drivers, input pumps, upload monitors and enforcing host-service workers have finished, including destruction after cancellation. The transport observes client loss through reclamation. Upstream upload accounting completes before the core releases the context. Sending an early response does not bypass this barrier. HTTP/1.1 does not accept the next request until this work finishes, even if a layer has ended both of its lanes but its handler or host-service calls are still running.

Once a layer is done with the client's upload, the rest of it is dropped: on HTTP/1.1 the codec drains or closes as it does after a deny (HTTP), on HTTP/2 the stream is reset with no error.

  • What a layer passes on is re-validated as strictly as a client request: an absolute http(s) URI; host, hop-by-hop and framing fields refused at the boundary (roxy derives them); the workload's limits applied; the body's trailers held to a client's rules (trailers). A WASM layer may not set content-length either (the body carries its own length); a service layer may, and the body it sends is held to it (service layers). chain.next fills in the scheme and authority from the exchange when the layer leaves them unset.
  • The response reaching the client edge must be final; a 1xx other than the 101 of a relayed upgrade fails closed as invalid_response.
  • What next returns is a response whoever produced it: the upstream's, the rules' refusal, or a 503 layer:<name> generated for a failure upstream, recorded on the flow as that refusal. The layer may pass it on or reshape it. A cut forward or an upstream lane ending without a head returns an error from next without making the layer faulty. A failed client request instead cancels the exchange.
  • A layer's response body to the client waits for the flow log like every forwarded body (audit backpressure).
  • Layers compile at config load and are cached across reloads while their file and settings are unchanged, so instance pools stay warm. A reload swaps the stack for new exchanges; exchanges in flight finish on theirs.

Content codings

On a flow some layer runs on and is subscribed to the body, roxy decodes the client's request body as the first such layer gets it and the response before it reaches the first subscribed layer on its way downstream, removing content-encoding; the body's length becomes unknown. A body no running layer is subscribed to is not decoded, and reaches the upstream or the client as sent.

  • The client gets an uncompressed response and the upstream an uncompressed request body; the origin's response to roxy stays compressed. Nothing re-encodes.
  • The codings and their strictness are the rules' (HTTP). Data that does not decode, or a decoded body over limits.max_request_body_bytes or limits.max_response_body_bytes, cuts the exchange like any failed body, also on a flow only an observer runs on.
  • A body in a coding roxy does not know passes through as it is, with its content-encoding; so does a 206 or any response with content-range.
  • The rules upstream of the layers read the response first and decode it for themselves (body rules).
  • No extension (permessage-deflate above all) is negotiated on a WebSocket a body-subscribed layer runs on (WebSockets).

http.decode_for_addons: false turns this off: layers see the bytes as sent, with their content-encoding, and WebSockets negotiate whatever extensions client and upstream agree on.

WebSockets

A layer gets the upgrade request in handle and passes it on with next (a service layer forwards it on its stream); the response from upstream is the 101. After it, the request body carries the client's bytes and the response body the upstream's for as long as the WebSocket is open. A layer reads, rewrites or holds back either direction as any body, refuses the upgrade by answering without next, and is left out of the WebSocket when its when skips the upgrade request. A subscription to one body puts the layer in that direction only: the other's bytes flow past it, however long its handler lives on relaying the direction it is in.

  • A layer that turns the upstream's 101 into another status fails the exchange closed (503 from layer:<name>) and roxy closes the upstream WebSocket; a 101 with no upgrade from upstream fails closed too.
  • Only Upgrade: websocket is an upgrade for the layers. A request asking for any other upgrade (h2c, say) is an ordinary request roxy forwards once it strips the upgrade, with its body and the usual body cap.
  • The bodies carry raw WebSocket frames. Frames from the client are masked, so their payload reads as sent only from the upstream's side.
  • A layer must stream both bodies at once: the request body ends only when the client closes, while the response streams all along (the roxy-addon SDK does this). Holding bytes back until more arrive stalls an interactive protocol.
  • The layer's head deadline does not limit the relayed bodies; the relay's idle timeout still applies. When the relay ends, roxy closes the client's connection whether or not the layers have ended their bodies; bytes already on their way get a second to arrive.

Failure

  • Every failure is closed. A trap, an exceeded budget, a second next or respond, a missing capability, a host failure, a head the host refuses, a body stream that is not the host's, a missing response, bytes on an unsubscribed body, a handler that returns still holding a body stream or a pending response, or a cancelled exchange is a LayerError: a 503 on the lane downstream of the layer before the response head (recorded as a deny, whatever a layer there makes of it), a cut body after it.
  • A client that gives up cancels the exchange. The guest is stopped, its instance discarded, the slot freed. No layer_error is logged.
  • No clean end for a failed body. A guest body ends with an error once its exchange has failed; a response body the guest produces (bytes or a stream) holds its end until the handler returns, so a trap after the last byte still cuts it. An open lane has unknown wire length, even for an empty declared body, until its producer ends cleanly. HEAD and bodiless statuses commit at the head, but their internal bodies must still finish within the body idle timeout. A streamed body is complete only through finish: dropped unfinished, it is cut where it stopped, the layer's own doing (reason: forward_aborted or answer_aborted), not a failure.
  • A cut forward gets no response. A request body passed to next that the guest drops without finish is cut at the upstream, and nothing comes back for it: next fails for the guest (error.internal), which may answer itself, and its answer stands. A body the guest passed through that fails behind it (the client gave up) is cut the same way, at the client's fault.
  • An instance that failed its exchange is discarded, never reused.
  • Layers see canonical heads and body streams, never wire bytes, and have no filesystem, sockets or environment: all their I/O is next, endpoints and flow.
